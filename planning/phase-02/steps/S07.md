## الهدف والسبب

حصر الوصول حسب نوع الحساب وتأكيد البريد وحالة التاجر وملكية المورد، مع قراءة الحالة الفعلية من SQL في كل طلب.

## مصادر واعتمادات

## Scope

AdminOnly وVerifiedCustomer وApprovedMerchant وVerifiedMerchantSetup؛ Pending/ChangesRequested المؤكد يستطيع تجهيز حسابه، ولا يصبح Approved بتأكيد البريد. يضاف AccountAccessStatus (Active/Suspended/Deleted) لغرض guard ومصفوفة S07 فقط، دون أوامر حذف/تعليق؛ S09 تنفذ انتقال الحذف والزمن والجدولة. الحالات غير النشطة وحالة Merchant Suspended تمنع login/refresh/طلبات جلسة سابقة.

## الشرح قبل التنفيذ

أسماء السياسات في public Application.Identity.Contracts ليمر استعمال Merchants عبر الحد المعتمد؛ التنفيذ Framework في Api.Identity، والحالة Merchant عبر عقدها العام دون Entity. Profile الهوية للعميل المؤكد وMerchant account/entitlement وAdmin session ومسارات قراءة الجلسات المملوكة موارد فعلية. Session IDs ليست refresh credentials؛ لا digest أو token في DTO. UserId من principal المعاد بناؤه من SQL فقط، وطلب مورد جلسة لغير المالك404. لا استثناء Admin لملكية جلسات الآخرين.

## تسلسل التنفيذ

Enum وcolumn additive default Active يحفظ سلوك الصفوف السابقة، وguard SQL للمستخدم وMerchant، ثم policies وعقود query وendpoints. fixtures تستعمل UserManager/SQL وتمثل Approved/Suspended/Deleted بلا approval API. مصفوفة HTTP للزائر وغير المؤكد والعميل المؤكد وPending/Approved/ChangesRequested/Rejected والتعليق/الحذف وAdmin، وحقن claims/UserId/roles وملكية الموارد. الاختبارات تشمل حالة تتغير بعد إصدار cookie.
