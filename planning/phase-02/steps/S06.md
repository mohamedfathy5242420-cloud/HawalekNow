## الهدف والسبب

حماية cookies من CSRF وحصر طلبات الهوية الحساسة، مع عدادات حساب دائمة في SQL وحدود IP داخل كل instance.

## مصادر واعتمادات

D005/D014–D016، وS05 Verified على9d97f82 و193 اختبارًا ناجحًا، و[تسليم S06](../handoffs/S05-to-S06.md) InternalReady. راجعت توثيق Microsoft الرسمي لـantiforgery وrate limiting وproxy للـ.NET10 قبل الكود.

## Scope

IAntiforgery.ValidateRequestAsync عبر authorization filter عامة لكل controller mutation، بما فيها anonymous register/login/OTP ومسارات S08/S09 المستقبلية. GET identity/csrf على HTTPS يعيد requestToken وheaderName فقط؛ cookie __Host- HttpOnly Secure Strict، وهو token CSRF وليس JWT/refresh. بعد تغير المستخدم أو انتهاء access، يعاد طلب CSRF وفق principal الحالي. quotas لكل عنوان اتصال: التسجيل5/10د، الدخول10/د، طلب رمز5/15د، التحقق20/10د، refresh30/د. لا queue أو بحث تجاري أو Headers موثوقة عشوائيًا.

## الشرح قبل التنفيذ

AddAntiforgery وDataProtection وRateLimiter من shared framework دون حزم إضافية. مفاتيح DataProtection ثابتة خارج Git؛ Production يحتاج Security:KeyRingPath مطلقًا ومخزنًا محميًا، وDevelopment يستخدم إعداد المنصة إن لم يحدد. اختبارات Program تستخدم provider مؤقتًا مملوكًا للمضيف، واختبار persistence مستقلًا بمجلد عشوائي مملوك. لا تعطيل Secure أو تجاوز CSRF في الإنتاج. RateLimiter بعد Routing وقبل المصادقة/المعاملات؛ RemoteIpAddress من الاتصال فقط، وX-Forwarded-* لا تفعل تلقائيًا في الكود. لا حماية موزعة أو DDoS مفترضة.

## تسلسل التنفيذ

تكوين browser protection وendpoint CSRF وrate metadata، ثم helpers ترسل CSRF حقيقية، واختبارات missing/invalid/cross-client/principal change و429/spoofed headers/HTTPS. فحص registration concurrency يبقى تحت SQL حقيقية مع peer contexts منفصلة حتى لا يصبح اختبارًا لكسر quota. لا تخفيف لقواعد SQL أو HTTP الأصلية.
