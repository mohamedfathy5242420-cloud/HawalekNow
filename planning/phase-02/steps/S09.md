## Scope

Customer/Merchant فقط؛ Admin self-delete403. AccountDeletion وaudit تقني مقتضب IDs/UTC/kind بلا بيانات دخول؛ endpoints DELETE identity/account بكلمة المرور وPOST recovery/request وrecovery/verify بغرض ثابت وAccountType صريح. لا متجر/منتج/بلاغ حقيقي أو سياسة حذف تجارية مستقبلية.

## الشرح قبل التنفيذ

الحذف يضع Deleted ويحفظ deadline وgeneration وaudit وOutbox schedule intent ويلغي sessions وOTP في معاملة واحدة. المعالج يسجل job SQL تحمل UserId وgeneration فقط؛ قد تتكرر الجدولة عند فقد ACK، لذا job تعيد فحص الحالة والنسخة والموعد. الاسترجاع قبل deadline فقط وبقفل الحالة، يلغي أهلية job دون إعادة أي session. عند الموعد نفسه ينتهي حق الاسترجاع. audit تحتفظ بمعرفات تقنية ونوع الانتقال والوقت فقط.

## تسلسل التنفيذ

Domain state rules ثم ports/commands؛ EF mappings وmigration additive؛ purge يتبع ترتيب identifier locks ثم user-state lock، ويكتب HMAC tombstones ويحذف Identity children وملف MerchantAccount الفارغ عبر عقد Merchants العام في SQL واحدة. binding ثابت لمفتاح الحجز يرفض تغييره بصمت؛ لا مفتاح في Migration. SubjectId عام اختياري للـOutbox يسمح بتنظيف ciphertext الهدف، مع association للرسائل القديمة بفك آمن داخل المعاملة؛ فشل المفتاح يفشل purge دون حذف جزئي. اختبارات الحدود والغرض والتزامن وrollback وworker restart والـjobs المكررة؛ لا EnsureDeleted أو بيانات تجارية مستقبلية. مصادر Hangfire الرسمية تؤكد Schedule persistent وat-least-once؛ لا exactly-once.
