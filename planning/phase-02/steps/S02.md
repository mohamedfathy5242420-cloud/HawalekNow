تأسيس Admin الأول بإجراء مشغل مقصود وإعدادات أسرار محلية، دون أي بيانات دخول ثابتة أو تعديل حساب موجود.

## Scope

AdminSeeder داخل Infrastructure.Identity وأمر --seed-admin في Program؛ إعدادات Environment فقط في أمثلة التشغيل. لا endpoint إدارة أو منح دور من عميل HTTP، ولا تشغيل تلقائي يعيد ضبط بيانات.

## الشرح قبل التنفيذ

Bootstrap إجراء تشغيل موثوق، مختلف عن التسجيل العام. قفل SQL مملوك للمعاملة يسلسل التنافس؛ وجود أي Admin يحول التشغيل إلى Unchanged دون تحديث password أو SecurityStamp أو RowVersion. جلسة الشرح التفصيلية بعد تسليم المرحلة.

## تسلسل التنفيذ

التحقق من الإعداد قبل SQL، ثم قفل bootstrap داخل المعاملة، وفحص Admin قائم، وإنشاء حساب مؤكد البريد عبر UserManager عند عدم وجوده. إعداد ناقص أو خاطئ يفشل برسالة ثابتة وexit 1 دون echo للأسرار. لا ينشئ قاعدة أو يطبق Migration ضمن bootstrap.

## سجل التنفيذ والمراجعة

بدأ بعد تحقق S01 وCommit 9b64c17. لا بيانات Admin حقيقية أو إعدادات ثابتة مضافة إلى Git؛ اختبارات bootstrap تستعمل قيمًا عشوائية وقواعد معزولة. اختبار التنافس أنشأ Admin واحدًا فقط، والتشغيل التالي بإعدادات مختلفة لم يغير Id أو الاسم أو البريد أو PasswordHash أو SecurityStamp أو RowVersion؛ كلمة المرور الأصلية ظلت صالحة والجديدة مرفوضة. اختبارات الإعداد رفضت النقص والاسم والبريد وكلمة المرور الخاطئة قبل SQL، مع عدم إنشاء حساب. Program الفعلي شُغّل كعملية مستقلة مرتين، ثم بلا كلمة مرور؛ اختبارات المخرجات رفضت ظهور Username وEmail وPassword.

أمر --seed-admin ينتهي قبل تشغيل خادم HTTP، ويتطلب إعداد SQL موجود وMigration مطبقة. لا يطبق Migration ولا ينشئ قاعدة ولا يسجل SQL/Host logs. Console يطبع إحدى رسالتين ثابتتين فقط بنتيجة الأمر، دون Exception أو قيم أو سياق؛ لا توسعة لسياسة Serilog/Pipeline أو عقد أخطاء HTTP. bootstrap المحلي الموثوق وحده ينشئ Admin مؤكد البريد؛ التسجيل العام لا يقبل هذا الخيار.
