## الهدف والسبب

تسجيل دخول مستقل لكل AccountType وجلسات SQL مع JWT وrefresh rotation داخل HttpOnly Secure cookies.

## مصادر واعتمادات

D005/D014–D016 وS04 Verified، Commit 1a8564b و[تسليم S05](../handoffs/S04-to-S05.md) InternalReady. تصميم المرحلة والقيم التقنية موثقة قبل التنفيذ.

## Scope

JWT access خمس دقائق، refresh سبعة أيام مع حد عائلة مطلق 30 يومًا. cookie names تبدأ __Host- وPath=/ وHttpOnly وSecure وSameSite=Strict دون Domain. refresh عشوائية 256-bit، تخزن SHA256 فقط مع selector؛ كل تدوير يستهلك القديمة ذريًا، وإعادتها الصحيحة تلغي العائلة كلها. الجلسة تمثل العائلة. الدخول يسمح للحساب غير المؤكد بجلسة محدودة؛ S07 تحرس السياسات. لا OAuth server أو تفويض لخدمات خارج النظام.

مدخل login هو identifier: بريد للعميل وAdmin، وبريد أو Username للتاجر وفق المتطلبات قسم3. تفرد AccountType يجعل lookup منفصلًا؛ صيغة username ASCII تستبعد @ فلا التباس بين مساري المطابقة. لا تغيير AccountType من بيانات JWT أو body آخر.

## الشرح قبل التنفيذ

التوقيع HS256 بمفتاح 32 bytes مستقل مطلوب خارج Git، مع issuer/audience مطلوبين ورفض alg آخر وClockSkew صفر ووقت قابل للتحكم. middleware يقرأ cookie فقط ويرفض fallback Authorization header، ويتحقق من SQL للجلسة والمستخدم في كل طلب محمي؛ الإلغاء يسري على الطلب التالي، ولا يدعي إيقاف طلب بدأ قبل commit. لا Tokens في Body أو logs. SQL lock لحالة المستخدم يوحد login/rotation/revoke؛ HTTPS فعلي في الاختبار بشهادة اختبار محلية موثوقة خصيصًا دون تعطيل Secure أو قبول أي شهادة.

## تسلسل التنفيذ

مراجعة JwtBearer 10.0.14 وIdentityModel 8.19.2 وتراخيص MIT وأمثلة التسجيل الرسمية، ثم تثبيت graph. كيانات الجلسة/الرمز وmapping وMigration additive، service وhandlers، cookie boundary وJWT middleware، ثم اختبارات signature/expiry/issuer/audience/rotation/concurrency/replay/HTTPS وعدم تسريب. CSRF وHTTP rate limits تأتي في S06 مباشرة قبل تسليم المرحلة.
